Feature — cross-store section search機能 — store 横断セクション検索

Let the cheap model search. Save the expensive one for judgment. 検索は安いモデルに任せる。高いモデルは判断に使う。

Store Search is how the AI finds things in your accumulated records — decisions, research, specs. It stacks three methods (plain grep, a full-text index, a document ledger), and when one comes up empty it automatically moves to the next. We don't claim the index beats grep — measured head-to-head, it doesn't. It earns its keep in exactly two situations: when your records have grown to the ~1,500-document scale, and when a cheap model is doing the searching. With few documents, grep alone is enough.

Store Search は、AI が蓄積した記録（決定・調査・仕様）から目当てを探し出す仕組み。索引なしの grep・ 全文索引・文書台帳の 3 つを重ね、どれかが 0 件でも止まらず次の手に自動で進む。「索引は grep より強い」とは言わない — 実測で比べたら、勝てなかった。効く場面はちょうど 2 つ：記録が 1,500 文書規模に育ったとき、そして安いモデルに検索させるとき。文書が少なければ grep で足りる。

What changed: when a search finds nothing, it now loosens the query and retries instead of giving up silently; formal decision records rank above working notes; session scratch files are out of the index; and related documents are followed link by link. Those four fixes took the cheapest model from 4/10 to 10/10 at best. And across a full 3-model × 3-effort sweep, effort barely mattered — haiku's lowest setting tied opus 4.8's highest.

何を変えたか：検索が 0 件のとき黙って諦めず、条件を緩めて自動で再検索する。正式な決定記録を 作業メモより上位に出す。セッションの一時メモを索引から外す。関連文書を芋づるで辿る。この 4 つの 改善で、いちばん安いモデルの成績が 4/10 から最高 10/10 まで上がった。さらに 3 モデル × effort 3 段階の総当たりでは effort はほぼ効かず、haiku の最低設定が opus 4.8 の最高設定と同点だった。

01

What it is — one layer in a fail-open stackこれは何か — 0 件でも止まらない検索層の 1 つ

Not an index that beats grep — measured head-to-head, it doesn't. A search layer that mixes grep, a full-text index, and a document ledger, falling open to the next when one comes up empty.grep に勝つ索引ではない。実測で正面から比べても、勝たない。grep・全文索引・文書台帳を組み合わせ、どれかが 0 件でも次へ開いたまま流す検索層。

0Routerルーター

A tiny guide injected at session start: census questions go to the ledger, content questions go here. No wholesale context dumping.セッション開始時に注入される小さな案内。数える質問は台帳へ、内容の質問はここへ。コンテキストの全投入はしない。

1Ledger台帳

A deterministic, complete document ledger for counting, auditing, and existence guarantees — measured to be where index-based navigation actually wins.数える・監査する・存在を保証するための決定論的な全数台帳。索引をたどる探索が実測で勝つのはここ。

2Store Search (this)Store Search（本機能）

Full-text section search over every store, ranked by BM25, returning exact line ranges — so the agent reads the section, not the whole file.全 store を対象にした全文セクション検索。BM25 で順位付けし、行範囲を返す。エージェントは全文でなく、セクションだけを読む。

  • Cross-project by construction: one index spans every project store on the machine. That reach is real only against the harness's own previous design — a bare grep -r also reaches across projects (R8 measured it: opus × grep scored 15/15 on cross-project questions). The honest comparison is "index vs. the old per-project combined text," not "index vs. grep."
  • 構造として横断的：索引はマシン上の全プロジェクト store を 1 つに束ねる。ただしこの到達力は、ハーネス自身の旧設計と比べたときにだけ成立する。索引なしの grep -r も横断はできる（検証ラウンド R8 の実測：opus × grep で横断 15/15）。誠実な比較は「索引 vs 旧・プロジェクト別 combined テキスト」であって、「索引 vs grep」ではない。
  • Japanese works out of the box: the trigram tokenizer matches CJK text directly, no morphological analyzer needed.
  • 日本語はそのまま動く。trigram トークナイザが CJK（日本語・中国語・韓国語）の文字を直接マッチさせるため、形態素解析器は不要。
  • Two conditions decide when this layer is worth it: many documents across many projects (the 1,500-document scale below), or a weak model doing the searching. Below that scale, grep over a handful of files is enough — don't reach for the index.
  • この層に価値が出る条件は 2 つに限る：複数プロジェクトにまたがる大量文書（1,500 文書級・後述）か、弱いモデルに検索させる場面。それ未満の規模なら、少数ファイルへの grep で足りる。索引に頼る理由がない。
02

How it works仕組み

Markdown is canonical. The index is derived, local, and disposable.正本は markdown。索引は派生物・ローカル・使い捨て。

1Write markdownmarkdown を書く

Decisions, research, specs land in the store as plain markdown — diffable, mergeable, git-managed. This is the only thing humans and git ever touch.決定・リサーチ・仕様は通常の markdown として store に入る。diff でき、マージでき、git が管理する。人と git が触るのはこれだけ。

→

2Index locallyローカルで索引化

A session-start hook rebuilds the SQLite FTS5 index from scratch — every heading becomes a section row with its line range. Built to a temp file, swapped atomically, skipped when nothing changed. Gitignored, like every derived artifact in the store.セッション開始 hook が SQLite FTS5 索引をゼロから再構築する。見出しごとに行範囲つきのセクション行になる。一時ファイルに構築して原子的に差し替え、更新がなければスキップ。store の他の派生物と同じく gitignore。

1,471 docs → 23,587 sections / 2.5s

→

3Query, then read the section引いて、セクションだけ読む

One wrapper command takes search terms, returns the top sections with BM25 rank, snippet, and exact line range. Terms too short for the trigram index fall back to a full scan automatically (16ms). Weak models never write SQL.ラッパーコマンドに検索語を渡すと、BM25 順位・抜粋・正確な行範囲つきで上位セクションが返る。trigram に短すぎる語は自動で全走査（16ms）へフォールバック。弱いモデルに SQL は書かせない。

<1ms / query · census 0.4ms

  • No migrations, ever: a schema change means "rebuild in 2.5 seconds," not a migration script.
  • マイグレーションは永遠に不要。スキーマ変更は「2.5 秒で作り直す」であって、移行スクリプトではない。
  • Fail-open like the rest of the harness: no SQLite or no FTS5 on the machine → the existing search path keeps working.
  • ハーネスの他と同じく fail-open（ある手段が使えなくても、次の手段へ自動で切り替わる設計）。マシンに SQLite や FTS5 がなければ、既存の検索経路がそのまま動き続ける。
  • Fail-open on empty hits, too: a 0-result query relaxes automatically (OR across terms) instead of returning a silent 0 and stopping — a weak-model failure mode measured directly in R8 (11 questions abandoned across 2 clean runs before the redesign).
  • 0 件でも fail-open：0 件を黙って返して止まるのではなく、自動で OR 緩和を試みる。再設計前の R8 では、弱いモデルが「黙って諦める」型の失点を出していた。汚染のない検証（以下「クリーン走行」）2 回で、11 問がこの型の失点だった。

04

Git and team scalegit と複数人

The rule is one line: the index is never committed.規律は 1 行：索引は絶対にコミットしない。

  1. Canonical vs. derived.正本と派生物。 Git manages markdown only. The index is a local cache with zero information value — delete it and lose nothing; the next session rebuilds it in 2.5 seconds.git が管理するのは markdown だけ。索引は情報価値ゼロのローカルキャッシュであり、消しても何も失わない。次のセッションが 2.5 秒で作り直す。
  2. No shared database.共有 db なし。 SQLite's classic weaknesses — concurrent writers, corruption on network filesystems — never arise: each machine builds its own index from the markdown it has, and the only writer is the local rebuild.sqlite の古典的弱点（同時書き込み・ネットワークファイルシステム上の破損）は構造上発生しない。各マシンが手元の markdown から自分の索引を作り、書き込むのはローカルの再生成だけ。
  3. Teammates never see it.メンバーは意識しない。 New members clone, open a session, and have their own index — no setup step, no shared infrastructure, no SQLite knowledge required.新メンバーは clone してセッションを開くだけで自分の索引を持つ。準備手順なし、共有インフラなし、sqlite の知識も不要。
  4. Access control stays in git.アクセス制御は git のまま。 Your index is built only from markdown you legitimately have — sharing granularity is decided by repository access, and the index can never widen it.索引は自分が正当に持つ markdown からしか作られない。共有の粒度はリポジトリのアクセス権が決め、索引がそれを広げることは決してない。
05

Limitations

Disclosed for the sake of honesty誠実性のための開示

  • The index alone does not beat grep (R8: ties on opus at 2.7x the tool calls, loses on haiku) and the "fewer search steps" claim from an earlier 1-run pilot did not replicate under 3-run binary scoring (R7: median tool calls 22 vs. 14 on opus, 23 vs. 23 on haiku). No token-count claim is made anywhere on this page.
  • 索引単独は grep に勝たない（R8：opus は同点だが tool 呼び出し 2.7 倍、haiku は負ける）。先行の 1 走行パイロットが出した「手数削減」の主張は、3 走行の二値採点で再現しなかった（R7：tool 呼び出し中央値 opus 22 対 14・haiku 23 対 23）。本ページのどこにも token 数削減の主張はない。
  • The rebench's first 3 runs were invalidated by store contamination (the store held R8's own answer ledger); the reported 7, 8, 10 comes from 3 clean runs after isolating and rebuilding. The store also grew since R8 and reused the same 10-question set — not a strict same-corpus, non-overfit comparison.
  • 再ベンチの初回 3 走行は、store 汚染（R8 自身の正解台帳が残存）で無効になった。報告している 7 点・8 点・10 点は、隔離・再構築後のクリーン 3 走行の数値。store は R8 時点から成長しており、同一 10 問セットも再利用している。厳密な同一コーパス比較でも、過適合なしの比較でもない。
  • 2–3 runs per cell (matrix: 2; rebench/R7/R8: 3) is enough to see a trend, not enough to test statistical significance.
  • 各条件 2〜3 走行（行列ベンチは 2、再ベンチ・R7・R8 は 3）は、傾向の確認まで。統計的な検定には足りない。
  • The trigram index needs 3+ characters; shorter terms fall back to a sequential scan (16ms measured — acceptable, but a real asymmetry).
  • trigram 索引は 3 文字以上が必要。短い語は全走査へフォールバックする（実測 16ms）。実用上は問題ないが、非対称であることに変わりはない。
  • The index is ~7x the source text on disk (85.5MB for 12.4MB of markdown) — cheap for a local cache, disclosed anyway.
  • 索引はソースの約 7 倍のディスクを使う（markdown 12.4MB に対し 85.5MB）。ローカルキャッシュとしては安いが、開示はする。
  • A 10x-scale synthetic stress test has not been run yet; the linear-vs-logarithmic scale argument beyond current size is extrapolation.
  • 10 倍規模の合成負荷試験は未実施。現規模を超える線形 vs 対数の規模議論は外挿にとどまる。
