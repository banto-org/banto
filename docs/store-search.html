Feature — cross-store section search機能 — store 横断セクション検索

Every document you ever wrote, one query away. No server. 書いてきた全ドキュメントを、クエリ 1 本で。サーバなしで。

The ai-context store grows without limit — decisions, research, specs, across every project. Store Search indexes every markdown section into a local SQLite FTS5 file and answers in under a millisecond, across project boundaries. The canonical data stays in git-managed markdown; the index is a throwaway local artifact, rebuilt from scratch in 2.5 seconds. Nothing to install, nothing to host, nothing committed.

ai-context store は決定・リサーチ・仕様と、プロジェクトを跨いで際限なく育つ。Store Search は その全 markdown をセクション単位でローカルの SQLite FTS5 ファイルに索引化し、プロジェクト境界を 越えて 1ms 未満で答える。正本は git 管理の markdown のまま。索引は 2.5 秒でゼロから作り直せる 使い捨てのローカル生成物であり、何もインストールせず、何も常駐させず、何もコミットしない。

01

What it is — and where it sitsこれは何か — どの層に立つか

The content layer of a three-layer design: route, count, then search.3 層設計の内容層。案内し、数え、それから検索する。

0Routerルーター

A tiny guide injected at session start: census questions go to the ledger, content questions go here. No wholesale context dumping.セッション開始時に注入される小さな案内。数える質問は台帳へ、内容の質問はここへ。コンテキストの全投入はしない。

1Ledger台帳

A deterministic, complete document ledger for counting, auditing, and existence guarantees — measured to be where index-based navigation actually wins.数える・監査する・存在を保証するための決定論的な全数台帳。索引ナビが実測で勝つのはここ。

2Store Search (this)Store Search（本機能）

Full-text section search over every store, ranked by BM25, returning exact line ranges — so the agent reads the section, not the whole file.全 store を対象にした全文セクション検索。BM25 で順位付けし、行範囲を返す — エージェントは全文でなくセクションだけを読む。

  • Cross-project by construction: one index spans every project store on the machine, so "which project solved this before?" becomes answerable — structurally impossible with the previous per-project search text.
  • 構造として横断的：索引はマシン上の全プロジェクト store を 1 つに束ねる。「これ、前にどのプロジェクトで解いた？」に答えられる — 従来のプロジェクト別検索テキストでは構造上不可能だった。
  • Japanese works out of the box: the trigram tokenizer matches CJK text directly, no morphological analyzer needed.
  • 日本語はそのまま動く。trigram トークナイザが CJK を直接マッチさせるため、形態素解析器は不要。
02

How it works仕組み

Markdown is canonical. The index is derived, local, and disposable.正本は markdown。索引は派生物・ローカル・使い捨て。

1Write markdownmarkdown を書く

Decisions, research, specs land in the store as plain markdown — diffable, mergeable, git-managed. This is the only thing humans and git ever touch.決定・リサーチ・仕様は素の markdown として store に入る。diff でき、マージでき、git が管理する。人と git が触るのはこれだけ。

→

2Index locallyローカルで索引化

A session-start hook rebuilds the SQLite FTS5 index from scratch — every heading becomes a section row with its line range. Built to a temp file, swapped atomically, skipped when nothing changed. Gitignored, like every derived artifact in the store.セッション開始 hook が SQLite FTS5 索引をゼロから再構築する。見出しごとに行範囲つきのセクション行になる。一時ファイルに構築して原子的に差し替え、更新がなければスキップ。store の他の派生物と同じく gitignore。

1,471 docs → 23,587 sections / 2.5s

→

3Query, then read the section引いて、セクションだけ読む

One wrapper command takes search terms, returns the top sections with BM25 rank, snippet, and exact line range. Terms too short for the trigram index fall back to a full scan automatically (16ms). Weak models never write SQL.ラッパーコマンドに検索語を渡すと、BM25 順位・抜粋・正確な行範囲つきで上位セクションが返る。trigram に短すぎる語は自動で全走査（16ms）へフォールバック。弱いモデルに SQL は書かせない。

<1ms / query · census 0.4ms

  • No migrations, ever: a schema change means "rebuild in 2.5 seconds," not a migration script.
  • マイグレーションは永遠に不要。スキーマ変更は「2.5 秒で作り直す」であって、移行スクリプトではない。
  • Fail-open like the rest of the harness: no SQLite or no FTS5 on the machine → the existing search path keeps working.
  • ハーネスの他と同じく fail-open。マシンに SQLite や FTS5 がなければ、既存の検索経路がそのまま動き続ける。

Measured, honestly実測 — 正直に

Prototype benchmark, 2026-07-02: same fixed 10 questions as prior rounds, two models, against the existing search.プロトタイプ実測（2026-07-02）。先行ラウンドと同一の固定 10 問・2 モデルで、既存検索と突き合わせた。

Conditions: "FTS5" = section search + reading only the returned line ranges (whole-file reads forbidden). "Existing" = grep over the per-project combined text, whole-file reads allowed. Census questions (5) used filesystem scans in both conditions; the difference loads entirely onto the 5 content-investigation questions. Answer keys were fixed immediately before the runs.

条件：「FTS5」= セクション検索 + 返された行範囲だけを読む（全文は読まない）。「既存」= プロジェクト別結合テキストの grep + 全文 Read 可。census 5 問は両条件ともファイル走査のため、条件差は内容調査 5 問にのみ載る。正解キーは走行直前に固定。

  • Accuracy is equal (39/40 overall) — while FTS5 searched a corpus 3.4x wider (1,471 documents across every project, vs. 433 in the per-project text) at the same cost. Cross-store reach came for free.
  • 精度は同等（総計 39/40）。しかも FTS5 は 3.4 倍広いコーパス（全プロジェクト 1,471 doc、既存はプロジェクト内 433 doc）を同コストで検索している。横断到達力は無料でついてきた。
  • Tokens did not drop (opus: −0.08%, haiku: +2.8%). The "read sections, save tokens" hypothesis did not materialize at this document size — decision records are only tens of lines, so section reads ≈ whole reads. This replicates, for the third time, the earlier finding that index type doesn't change content-investigation cost.
  • トークンは減らなかった（opus −0.08%・haiku +2.8%）。「セクション読みで token 削減」仮説は、この文書サイズでは成立しない — 決定記録は数十行で、セクション読み ≒ 全文読み。「索引の種類は内容調査のコストを変えない」という先行実測を三たび再現した。
  • Tool calls did drop (14 vs 18 on opus, 17 vs 26 on haiku): ranked sections mean less grep juggling to find the right document.
  • tool 呼び出し数は確実に減った（opus 14 vs 18・haiku 17 vs 26）。順位付きセクションが返るため、正しい文書へ届くまでの grep の試行錯誤が減る。
  • The single miss: the weak model stopped at a derived record that quoted the question itself instead of the primary source — a known weak-model failure mode observed in earlier rounds, not an index defect.
  • 唯一の失点は、弱いモデルが一次資料でなく「質問文そのものを引用した派生記録」で停止したもの。先行ラウンドで観測済みの弱モデル固有の失敗型であり、索引の欠陥ではない。

So why adopt it? Because the case was never token savings — the measurements killed that claim before it shipped. The case is what the old design cannot do at all:

では、なぜ採用するのか。根拠は最初から token 削減ではない — その主張は出荷前に実測が棄却した。根拠は、旧設計には原理的にできないこと：

aCross-store reach横断到達力

One query spans every project's memory. Per-project search text can never answer "where did we solve this before?"クエリ 1 本が全プロジェクトの記憶に届く。プロジェクト別の検索テキストは「前にどこで解いた？」に永遠に答えられない。

bScale headroom規模ヘッドルーム

The combined text grows linearly and is already megabytes; the index answers in sub-millisecond regardless, and section reads start paying off on long documents (hundreds of lines) the store keeps accumulating.結合テキストは線形に育ち、すでに MB 級。索引は規模によらず 1ms 未満で答え、セクション読みは store に増え続ける長文（数百行級）で効き始める。

cOne artifact, both jobs1 生成物で 2 役

Counting and content search share the same file — and the same metadata enables deterministic consistency gates (e.g., "an accepted spec has a newer contradicting decision") in one SQL statement.数える仕事と内容検索が同じファイルで済む。同じメタデータで「accepted の spec より新しい矛盾する決定がある」といった一貫性ゲートを SQL 1 本で張れる。

04

Git and team scalegit と複数人

The rule is one line: the index is never committed.規律は 1 行 — 索引は絶対にコミットしない。

  1. Canonical vs. derived.正本と派生物。 Git manages markdown only. The index is a local cache with zero information value — delete it and lose nothing; the next session rebuilds it in 2.5 seconds.git が管理するのは markdown だけ。索引は情報価値ゼロのローカルキャッシュであり、消しても何も失わない。次のセッションが 2.5 秒で作り直す。
  2. No shared database.共有 db なし。 SQLite's classic weaknesses — concurrent writers, corruption on network filesystems — never arise: each machine builds its own index from the markdown it has, and the only writer is the local rebuild.sqlite の古典的弱点（同時書き込み・ネットワークファイルシステム上の破損）は構造上発生しない。各マシンが手元の markdown から自分の索引を作り、書き込むのはローカルの再生成だけ。
  3. Teammates never see it.メンバーは意識しない。 New members clone, open a session, and have their own index — no setup step, no shared infrastructure, no SQLite knowledge required.新メンバーは clone してセッションを開くだけで自分の索引を持つ。準備手順なし、共有インフラなし、sqlite の知識も不要。
  4. Access control stays in git.アクセス制御は git のまま。 Your index is built only from markdown you legitimately have — sharing granularity is decided by repository access, and the index can never widen it.索引は自分が正当に持つ markdown からしか作られない。共有の粒度はリポジトリのアクセス権が決め、索引がそれを広げることは決してない。
05

Limitations

Disclosed for the sake of honesty誠実性のための開示

  • Numbers on this page are prototype measurements (2026-07-02, 1 run per cell); the production wiring ships the same mechanism with atomic swap and freshness checks.
  • 本ページの数値はプロトタイプ実測（2026-07-02・各セル 1 走行）。本番配線は同じ機構に原子的差し替えと鮮度チェックを加えて出荷する。
  • No token savings at current document sizes — adoption rests on reach, scale headroom, and fewer search steps, not cost.
  • 現状の文書サイズでは token 削減なし。採用根拠は到達力・規模ヘッドルーム・検索手数の削減であり、コストではない。
  • The trigram index needs 3+ characters; shorter terms fall back to a sequential scan (16ms measured — acceptable, but a real asymmetry).
  • trigram 索引は 3 文字以上が必要。短い語は全走査フォールバック（実測 16ms — 実用上問題ないが、非対称は非対称）。
  • The index is ~7x the source text on disk (85.5MB for 12.4MB of markdown) — cheap for a local cache, disclosed anyway.
  • 索引はソースの約 7 倍のディスクを使う（markdown 12.4MB に対し 85.5MB）。ローカルキャッシュとしては安いが、開示はする。
  • A 10x-scale synthetic stress test has not been run yet; the linear-vs-logarithmic scale argument beyond current size is extrapolation.
  • 10 倍規模の合成負荷試験は未実施。現規模を超える線形 vs 対数の規模議論は外挿にとどまる。

Adopted on evidence — including the evidence against it.実測で採用した — 不利な実測も含めて。

The token-savings claim died in measurement before it could ship. What survived is what the old design could never do.token 削減の主張は出荷前に実測で死んだ。生き残ったのは、旧設計には決してできないことだった。
