Plugin toolsプラグインの道具

Build plugins. Audit them rigorously. プラグインを作る。正確に監査する。

Banto is built with the same discipline it sells. Two skills keep its own surface — and yours — in shape: plugin-dev scaffolds and refactors skills, hooks, and plugins against official best practices; plugin-audit scores them on 14 quality axes, with the judgment calls delegated to a fresh agent so a skill never grades its own homework.

Banto は、売っているのと同じ規律で作られている。2 つの skill が、自分の — そしてあなたの — 表面を整える： plugin-dev は skill / hook / plugin を公式ベストプラクティスに沿って scaffold・改修し、 plugin-audit は 14 の品質軸で採点する。判定は fresh agent に委ねるため、skill が自分の答案を自分で採点しない。

Build, grade, refactor — until it earns a clean report.作り・採点し・直す — クリーンな報告になるまで。

Why the score is trustworthyなぜ採点が信頼できるか（＝正確さの根拠）

Accuracy here isn't a claim — it's a property of how the audit is built.ここでの「正確さ」は主張ではなく、監査の作りそのものから来る性質。

  1. Reviewer = a fresh agent.採点者は fresh agent。 Judgment axes go to an independent sub-agent, so a skill never grades its own homework — the main session's self-evaluation bias is removed. Votes are tiered (opus ×1 / sonnet ×3 / haiku ×5), which also surfaces cheap-model degradation.判定軸は独立サブエージェントが下す — skill が自分の答案を自分で採点しない（メインの自己評価バイアスを排除）。投票は tier 別（opus ×1 / sonnet ×3 / haiku ×5）で、安いモデルの劣化も浮かせる。
  2. Static axes are deterministic.静的軸は決定論的。 Structure, paths, usage, permissions, hygiene are computed by scripts (regex / git log) — same input, same result, no model in the loop.構造・パス・使用度・権限・衛生はスクリプト（regex / git log）が計算 — 同じ入力なら常に同じ結果・モデル不要。
  3. Routing precision is measured, not assumed.ルーティング精度は実測。 Axis 4 runs an eval-cases set (positive / negative / boundary) and reports real Precision / Recall / Forbidden numbers.Axis 4 は eval-cases（positive / negative / boundary）を回し、実数の Precision / Recall / Forbidden を出す。
  4. Tier sweep.tier 横断検証。 Routing is re-measured per model tier (haiku / sonnet / opus) — since Banto delegates to cheaper models, their degradation is a real production risk.routing をモデル tier 別（haiku / sonnet / opus）で再測定 — Banto は安いモデルへ委譲するため、その劣化が本番リスクになる。
  5. Boundary cases are weighted up.境界ケースを重視。 The eval set fixes a high boundary ratio — accuracy historically drops exactly where two skills nearly overlap, so that's where it's tested hardest.eval セットは境界比率を高く固定 — 精度は「2 つの skill がほぼ重なる」境界で落ちるため、そこを最も厳しく試す。

What's a HeavySkill? (Axis 5)HeavySkill とは？（Axis 5）

A skill structure for complex judgment — trade-offs, multi-perspective analysis — built on the parallel-reasoning + sequential-deliberation pattern of arXiv 2605.02396. Audited by Axis 5; generated by plugin-dev. Four required components:複雑な判断（トレードオフ・多視点分析）向けの skill 構造。並列推論 + 逐次審議の arXiv 2605.02396 パターンに基づく。Axis 5 が監査し、plugin-dev が生成する。必須の 4 要素：

1 · Activationfires only on a real goal fork — not for routine work真のゴール分岐のときだけ発火（routine では出ない）
2 · ParallelK=3–5 independent agents, each a distinct lens (not the same prompt ×K)K=3–5 の独立エージェント・各々別の視点（同一プロンプト ×K ではない）
3 · Deliberationre-derive a new answer from the perspectives — not a majority vote視点から新解を再導出 — 多数決ではない
4 · Outputconclusion-first, options table, risks — no "it depends"結論先行・選択肢表・リスク — 「場合による」禁止

Used only when the task earns it (complex + WORKFLOW + Agent tooling). A simple utility skill should stay simple — Axis 5 flags both missing and mis-applied HeavySkills.task が要求するときだけ採用（複雑 + WORKFLOW + Agent ツール）。単純な utility skill は単純なまま — Axis 5 は「足りない」も「誤適用」も拾う。

plugin-dev — scaffold & refactorplugin-dev — scaffold & 改修

Create a new skill, hook, or plugin from official templates — or refactor an existing one. It loops with plugin-audit so what it builds is graded as it is built.公式テンプレから skill / hook / plugin を新規作成、または既存を改修。plugin-audit と連動し、作りながら採点する。

scaffold生成 → audit監査 → refactor改修 → re-verify再検証 ↻loops until cleanクリーンになるまで反復

What it generates何を生成するか

  • a skill (standard, or the 4-component HeavySkill when the task is complex)skill（標準、または複雑なら 4 要素の HeavySkill）
  • hooks + hooks.json wiring; plugin.json; agentshook + hooks.json 配線・plugin.json・agent
  • the Layer-3 trio (skill + rule + hook) when something must be enforced, not just suggested何かを「提案」でなく「強制」すべきとき、Layer-3 の trio（skill + rule + hook）

Refactor mode改修モード

  • checks real usage, then proposes minimizing description / references / allowed-tools実使用を確認し、description / references / allowed-tools の最小化を提案
  • backward-compatibility first; applies edits, then re-verifies後方互換を優先・編集を適用して再検証
  • avoids over-engineering — a skill alone is a fine place to start過剰設計を避ける — skill だけで始めてよい
番
Lean by default. plugin-dev proposes the smallest thing that works and escalates to a trio or a HeavySkill only when the task earns it — the same anti-bloat instinct the audit enforces.既定で lean。plugin-dev は「動く最小」を提案し、trio や HeavySkill へは task が要求するときだけ昇格する — 監査が強制するのと同じ反・肥大の本能。
