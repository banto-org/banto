context-keeper — keeps the search-text layer honestcontext-keeper — 検索テキスト層の整合を保つ

context-keeper checks whether the search-text layer — full-combined.txt and sessions-cache/ — still matches {base}/decisions/ and {base}/docs/, and regenerates it if it has gone stale. It runs on the sonnet model.

context-keeper は検索テキスト層（full-combined.txt / sessions-cache/）が {base}/decisions/ と {base}/docs/ に追従しているかを確認し、鮮度が落ちていれば再生成する。sonnet モデルで動く。

01

Allowed tools許可ツール

ReadWriteGlobGrepBash
02

What it does何をするか

full-combined.txt refreshes only on SessionStart's daily throttle and on-demand at the start of search's deep path — it never auto-follows a write. context-keeper's freshness check compares its mtime against the newest file under decisions/docs, and separately checks each sessions-cache/<session_id>.txt against its matching JSONL.

full-combined.txt は SessionStart の日次スロットルと search の deep path 開始時のオンデマンド更新でしか動かず、書き込み直後には自動追従しない。context-keeper の鮮度チェックは、その mtime を decisions/docs 配下の最新ファイルと比較し、sessions-cache/<session_id>.txt は対応する JSONL と個別に比較する。

When regeneration is needed, it runs ai_context_combined.py --scope full, then verifies with Grep that the most recently written file's <<<FILE:...>>> marker is present in full-combined.txt. The former project-scope layer is retired since the search-layer-redesign spec, so it is out of scope here.

再生成が必要なら ai_context_combined.py --scope full を実行し、直近に書き込まれたファイルの <<<FILE:...>>> マーカーが full-combined.txt に存在することを Grep で確認する。旧 project scope は search-layer-redesign の仕様分岐で廃止済みのため対象外。

03

When it firesいつ動くか

verify consistency after a writefull-combined.txt looks staleregenerate sessions-cache a normal searcha simple file lookup

A normal search runs through the search skill; a simple file lookup is fine with a direct Read.

通常の検索は search skill が担う。単純なファイル参照は直接 Read で十分。

04

Invocation呼ばれ方

context-keeper is launched from the main session with the Agent tool, usually right after a batch of writes to decisions/ or docs/, or when the search skill suspects the text layer is stale.

context-keeper は本体セッションから Agent ツールで起動する。通常は decisions/ や docs/ へのまとまった書き込み直後、あるいは search skill がテキスト層の鮮度を疑ったときに呼ぶ。

// example invocation from the main session
Agent({
  subagent_type: "context-keeper",
  description: "Verify search-text layer after decision writes",
  prompt: "ai-context base: {base}. Just wrote 3 new files under {base}/decisions/. Verify full-combined.txt reflects them and regenerate if stale."
})
05

How it works仕組み

1. resolve {base}
→
2. check mtime freshness
→
3. regenerate (ai_context_combined.py)
→
4. verify marker with Grep
番

If the base can't be resolved from the prompt or from _ai-context-paths.sh --resolve, it does not write to a relative path — it reports "base unknown" to the parent and exits, the same degrade as research-agent.

プロンプトからも _ai-context-paths.sh --resolve からもベースが解決できない場合、相対パスへは書き込まない。「base unknown」と親に報告して終了する（research-agent と同じ degrade）。
