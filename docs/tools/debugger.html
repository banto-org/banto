debugger — root-cause fix, not symptom patchingdebugger — 症状ではなく根本原因を直す

debugger runs a reproduce → locate → fix → verify loop on errors, test failures, and unexpected behavior. It edits code directly, then re-runs to confirm the fix works. Model is inherited from the calling session.

debugger はエラー・テスト失敗・想定外の挙動に対して、再現 → 特定 → 修正 → 検証のループを回す。コードを直接編集し、再実行して修正が効くことを確かめる。モデルは呼び出し元セッションから継承する。

01

Allowed tools許可ツール

ReadEditBashGrepGlob
02

What it does何をするか

The process: capture the error message and stack trace, identify reproduction steps, locate the point of failure, implement the minimal fix, then verify it works. Along the way it analyzes logs, reviews recent code changes, forms and tests hypotheses, and adds debug logging strategically.

手順は、エラーメッセージとスタックトレースの把握、再現手順の特定、失敗箇所の特定、最小限の修正の実装、修正の検証の順。途中でログを分析し、直近のコード変更をレビューし、仮説を立てて検証し、必要ならデバッグログを戦略的に加える。

Every result includes five parts: the root-cause explanation, the evidence backing the diagnosis, a concrete code fix, a testing approach, and prevention recommendations. The focus stays on the underlying problem, not the symptom.

結果には常に 5 つの要素を含める。根本原因の説明、診断を裏付ける証拠、具体的なコード修正、テストの方針、再発防止の推奨事項。狙うのは症状ではなく根本的な問題の修正。

03

When it firesいつ動くか

got an errortest failedit doesn't workwhy does it fail/errorroot causestacktracecan't reproduce design discussionsnew feature implementation"why did it end up this way" about past decisionsgeneral-knowledge why-questionsa single-file typo

Design discussions route to architect; new features go through spec then self-driving implementation; "why did we decide this" routes to the search skill; general-knowledge why-questions route to research; a minor typo in one file is fine with a direct Edit.

設計議論は architect へ、新機能は spec を経て自走実装へ回る。過去の決定についての「なぜこうなったか」は search skill へ、一般知識の why 質問は research へ回る。単一ファイルの軽微なタイポは直接 Edit で十分。

04

Invocation呼ばれ方

debugger is launched from the main session with the Agent tool. Under odd-gate — when tests have failed repeatedly and Write/Edit is blocked — it is restricted to Read / Grep / Glob only, and returns a proposed diff for the parent to apply instead of editing directly.

debugger は本体セッションから Agent ツールで起動する。テストが繰り返し失敗して odd-gate が Write/Edit をブロックしている状況下では、Read / Grep / Glob のみに制限され、修正を diff として親セッションに返す（自分では Edit しない）。

// example invocation from the main session
Agent({
  subagent_type: "debugger",
  description: "Fix the flaky checkout test",
  prompt: "pytest tests/checkout_test.py is failing intermittently with a stale-cart error. Reproduce, locate the root cause, fix, and re-run to confirm."
})

How it works仕組み

1. capture error/trace
→
2. reproduce
→
3. locate failure
→
4. minimal fix (Edit)
→
5. re-run and verify (Bash)
番

Under odd-gate, step 4 changes: instead of editing, debugger returns a fix as a diff and advises that ODD_ALLOW_TEST_FAILURES=1 can escape the gate temporarily if a reason is stated.

odd-gate 下では手順 4 が変わる。編集する代わりに修正案を diff として返し、理由の明記を条件に ODD_ALLOW_TEST_FAILURES=1 で一時的にゲートを回避できると助言する。
