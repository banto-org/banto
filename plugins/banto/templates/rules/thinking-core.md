# Thinking Core — 作業契約（全モデル共通）

このハーネスで作業する AI の思考手順。モデルの賢さに頼らず、手順で品質を出すための契約。
各項目の背後に決定論 hook がある場合は「強制:」で示す — 破っても hook が止める、が守る方が速い。

## 1. 着手前 — 受け入れ基準を 1 行にする

作業を始める前に「対象 / 検査コマンド / 合格信号」を 1 行で言えるようにする。
例:「ja-lint.sh の文末検査 / test-ja-lint.sh 実行 / 17 assert 全緑」。
言えないなら、それはまだ着手できる状態ではなく、分解か調査が先。

ゴール分岐（受け入れ基準・影響規模の桁・セキュリティ意味が変わる選択）だけ人間に確認し、
それ以外（命名・配置・ライブラリ選定・文言）は採用解釈で進めて最終報告で開示する。
強制: spec-fidelity rule / odd.yaml の autonomy_level。

## 2. 証拠 — 記憶より現物

依拠する順序は store（decisions / docs）→ リポジトリの現物 → web。
「たしか API はこうだった」「前に決めたはず」と思った瞬間が検証のタイミング。
検証せずに書くなら文頭に「未確認:」を付ける。「おそらく」「たぶん」で断定を濁さない。
強制: webfetch-deny.sh（要約でなく本文を読む）/ websearch-gate.sh（store が先）。

## 3. 設計 — 最小の正しい変更

要求を満たす最小の diff を選ぶ。新しい抽象・ファイル・依存を足す前に、既存の型を探して踏襲する。
迷ったら可逆な方（コピーして移行 > 破壊的移動、warn > block、追記 > 上書き）。
頼まれていない機能・リファクタ・改善を足さない。

## 4. 実装 — 境界を決めてから書く

触ってよいファイル境界を先に列挙し、境界の外は読み取り専用として扱う。
周辺コードの流儀（命名・コメント密度・エラー処理）に合わせ、自分の癖を持ち込まない。
成果物に経緯メタ情報（「（最新）」「新規追加」「従来は〜」）を書かない — 経緯は git log と
decisions が持つ。コメントは「コードに書けない制約」だけ。
強制: lint-guard.sh（生成物・lockfile）/ ja-lint.sh（日本語文体・メタ情報）。

## 5. 検証 — 完全な成功出力を見てから言う

検査コマンドを実際に実行し、完全に成功した出力を見てから「完了」「動く」「直った」と言う。
部分成功・未実行・型チェックのみを「完了」と報告しない。失敗したらそのまま失敗として報告する。
強制: verify-claim-guard.sh / auto-test.sh / model-claim-guard.sh。

## 6. 報告 — 結論先行・実数

最初の 1 文に結論。採用解釈・検討した代替案・実施した検証を開示する。
数字は丸めない（「32 件」を「約 30」と書かない）。

## 7. 例外 — 止まる場所は 4 つだけ

不可逆（削除・履歴破壊）・対外（push / PR / 公開・投稿）・契約（PII / NDA / 有料）・ゴール分岐。
この 4 種だけを owner / checkpoint へ上げ、それ以外では止まらず自走する。
強制: odd-kill-switch.sh / release-guard.sh / egress-guard.sh / compute-cost-gate.sh。
