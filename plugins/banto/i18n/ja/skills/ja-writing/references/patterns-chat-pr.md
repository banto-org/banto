# 会話・PR 説明・commit メッセージのパターン

短い出力ほど型の効果が大きい。3 つの場面それぞれで形が違う。

## チャット応答（会話）

会話は自然な言葉でよい（文末規則の対象外）。ただし 3 点は常に守る:
結論を最初の 1 文に置く。問いの重さに応答の長さを比例させる（1 行で足りる問いに 3 段落を返さない）。
カタカナ英語で言い換え可能な語（イシュー・フィックス・アップデート）は日本語で言う。

> 良: 「直りました。原因は環境変数の読み込み順で、テスト 12 件全緑です。」
> 悪: 「ご質問ありがとうございます。まず状況を整理しますと、こちらのイシューは…」

## PR 説明

骨格: 何が変わるか（1 文）→ なぜ（1〜2 文）→ 検証（実行したコマンドと結果の実数）→ 影響範囲・
レビューで見てほしい点。

> 良: 「checkpoint の消費を /clear のみに限定する。resume が先に消費すると直後の /clear に
> 何も残らないレースの修正（詳細は decision 2026-07-08-160000）。test-idle-checkpoint-delivery.sh
> 17/17 緑。既存の checkpoint 形式に後方互換。」

diff から読み取れること（どのファイルを変えたか・行数）を繰り返さない。
書くのは diff に写らないこと — 意図・却下した代替案・検証結果。

## commit メッセージ

1 行目: `種別(範囲): 変更の要約`（50 字目安・現在形・何が変わるか）。
本文（必要時のみ): なぜこの変更か。What は diff が持つので Why だけ書く。

> 良: `fix(search): 0 件時の OR 緩和で誤った黙殺を解消`
> 悪: `修正` / `いろいろ更新` / `検索機能について、0件になる場合があったため、その対応を実施`

## 3 場面共通の禁止

謝罪・感謝の定型で始めない。「〜と思います」「たぶん」で断定を濁さない（不確実なら「未確認:」を
付けて事実と区別する）。同じ内容を言い換えて 2 回書かない。絵文字・「！」を成果物に使わない。
