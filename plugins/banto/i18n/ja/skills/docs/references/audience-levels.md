# 受け手レベル別の書き分け（L1 / L2 / L3）

日本語の資料は「何を書くか」より先に「誰が読むか」で形が決まる。書き始める前に受け手を
L1（非技術: 経営層・営業・顧客）/ L2（半技術: PM・情シス・発注担当）/ L3（技術: 開発者）の
どれかに固定し、文書全体で混ぜない。

## 判定基準

読み手がコードを書くなら L3、コードは書かないがシステム構成を判断するなら L2、
費用と効果だけを判断するなら L1。迷ったら 1 段下げる（L3 か L2 で迷えば L2）。

## 同じ内容の 3 通り

伝える事実:「検索インデックスを SQLite FTS5 に置き換え、検索が平均 1.8 秒 → 0.3 秒になった」

L1（非技術）— 効果と費用だけ。技術名詞を出さない:
> 資料検索の待ち時間を平均 1.8 秒から 0.3 秒に短縮。追加費用なし、既存データはそのまま。

L2（半技術）— 何を替えたかまで。仕組みの内部には入らない:
> 検索の仕組みを全文検索データベース（SQLite FTS5）に置き換え、平均応答 1.8 秒 → 0.3 秒。
> サーバ追加は不要で、既存の検索画面は変更なし。

L3（技術）— 判断根拠と再現手段まで:
> grep 逐次走査を SQLite FTS5（trigram tokenizer）へ置換。10 万文書で平均 1.8 秒 → 0.3 秒
> （bench/search-bench.sh・n=30）。インデックスは commit hook で差分更新、再構築は 40 秒。

## レベル別の禁止事項

L1 では技術名詞・英略語を出さない（どうしても必要なら「全文検索の仕組み」のように機能で言う）。
L2 では実装の内部構造（tokenizer・アルゴリズム名）に入らない。
L3 では逆に、根拠（計測条件・件数・再現コマンド）を省かない — L3 向けで根拠が無い文書は信頼されない。

全レベル共通: 数字は実数（「約 2 秒」でなく「1.8 秒」）、効果は before → after の対で示す。
