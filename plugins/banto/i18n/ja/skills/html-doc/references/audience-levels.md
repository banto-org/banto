# Audience Levels — 相手のレベルに合わせる

資料の失敗の大半は「書き手の解像度で書く」こと。**相手が翌朝、他人に説明できるか**を基準にレベルを選ぶ。
レベルは雛形（用途）から独立した**書き方の調整軸** — どの雛形（報告書/手順書/説明資料/提案書）もどのレベルでも書ける。言語（日本語/英語）とも独立。

## レベル判定

依頼文から推定し、推定したら冒頭の採用解釈として開示する。迷ったら**1段下げる**（L3で書いてL1に出す事故 >> 逆）。

| 手がかり | 推定 |
|---|---|
| 「社長に」「役員に」「クライアントの偉い人に」「決裁」 | L1 |
| 「先方PMに」「ディレクターに」「非エンジニアだけどわかってる人」 | L2 |
| 「チームに」「エンジニアに」「引き継ぎ」「技術レビュー」 | L3 |

## L1 — 経営層・非エンジニア

- **構成**: 結論（1文）→ 効果・影響（数字）→ お願いしたい判断 → 根拠は付録へ
- **文体**: 専門語ゼロ。固有ツール名は「○○（〜するための仕組み）」と一言添えるか用語集へ。1文40字以内目安
- **図**: 箱3〜5個のフロー1枚まで。シーケンス図・ER図は出さない。**図に結論を書き込む**（「ここがボトルネック」等の注釈）
- **数字**: 金額・工数・期日に変換して出す（「レイテンシ40%減」→「待ち時間が5秒→3秒」）
- **分量**: A4換算1〜2枚。スクロール3画面超えたら削る

## L2 — PM・ディレクター・半技術職

- **構成**: 結論 → 経緯 → 選択肢と判断根拠（採用/不採用の理由） → スケジュール影響 → next action
- **文体**: 専門語は使ってよいが初出時に半行の説明。「なぜそうしたか」を必ず書く
- **図**: フロー・ガント・状態遷移まで。1資料3枚まで
- **分量**: A4換算2〜4枚

## L3 — エンジニア

- **構成**: 結論 → 技術的詳細（省略しない） → 検証方法（再現コマンド・パス） → 既知の制約
- **文体**: 正確な用語をそのまま。コードブロック・パス・コミットhashを書く。曖昧さは「未確認:」を付けて区別
- **図**: シーケンス・ER・アーキテクチャ図OK。図より正確なテキスト（パス・型）が勝る場面では図を省く
- **分量**: 必要なだけ。ただし結論とTL;DRは必ず冒頭

## 共通ルール

- どのレベルでも**冒頭に結論box（summary）必須**。「読み終わらないと結論がわからない」資料を出さない
- どのレベルでも**最後に next action / 判断依頼**を置く
- 1つの資料に複数レベルを混ぜない。混在が必要なら「本編L1 + 付録L3」に分離する
- **クライアント向け（社外に出る）資料は pii-protection ルール適用**: 内部メンバー名・他案件名・他社名・単価をマスク（「担当者A」「○○社」）。egress-guard が registry 命中で止めるが、止まる前に自分でマスクする
