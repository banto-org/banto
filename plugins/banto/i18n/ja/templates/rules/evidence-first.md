# Evidence First Rule（証拠優先ルール）

返信時だけのルールではなく、**作業全般のデフォルト**。実装・設計・修正・レビューの途中で、古い / 欠落している可能性がある記憶（バージョン、API の形状、過去のプロジェクトでの決定、「ベストプラクティス」）に頼ろうとした瞬間 — 「たしか最新は vX のはず」「この API はこう動くはず」「前に Z と決めたはず」 — が、それに依拠する**前**に検証するタイミングである。指示を待たずに下の順序を実行する。

## 検索順序（厳格）

1. **まずローカル store を検索する** — `search` skill（`/search <query>`）。過去の決定・過去のリサーチ・プロジェクトの経緯はここでカバーする。
2. **鮮度が重要な領域だけ web へエスカレーションする** — `search` が確信の持てるヒットを返さず、**かつ**その事実が鮮度に敏感な場合（AI / LLM の挙動、ライブラリ / フレームワークのバージョン、リリースノート、「ベストプラクティス」、トレンド、比較）、`research` skill に委譲する。`research` 自身のステップ 1 も「まず `search`」であり、store-first の順序は保たれる。

鮮度が重要でない純内部の問い（「何を決めたか」「なぜこうなっているか」）はステップ 1 だけで完結する — web へエスカレーションしない。`search` が何も見つけなければ、その旨を明確に伝える。

WebFetch は決定論的にブロックされる（`webfetch-deny.sh` — 検証不能な小型モデルの要約を返すため）。URL の本文は `webread` で読む。WebSearch は URL を*見つける*用途には使ってよい（`websearch-gate.sh` が先に `search` を促すが block はしない）。大規模な調査は research-agent に委譲する。

## 禁止事項

- 知識カットオフの記憶だけで答える、またはコードを書く
- 「一般的にはこう言われている」「おそらく」「たぶん」で断定する（不確実なら「Unverified: / 未確認:」を付ける）
- メインセッションから直接大規模な WebSearch 調査を実行する（research-agent に委譲する）

対象外: 外部や記憶している事実に依拠しない機械的なファイル編集、目の前のコード検索だけで答えられる問い、単純な挨拶や雑談。
