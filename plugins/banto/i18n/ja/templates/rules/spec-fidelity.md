# Spec Fidelity（仕様準拠）— 仕様への忠実性

## 停止トリガー（これだけ）
- ゴール分岐が存在する → 事前に確認する
- 既存の `decisions/` と矛盾する → 過去の決定を再確認する
- それ以外 → 採用解釈で進める

## ゴール分岐の例（停止する）
- A/B の選択で受け入れ基準が変わる
- A/B の選択で影響範囲の桁が変わる
- セキュリティ / コンプライアンス上の意味が変わる
- ユーザー固有の業務知識（社内規則・契約・法規制）に依存する

## ゴール分岐ではない例（進める）
- 命名、ファイル配置、ライブラリ選定
- ログ / エラーメッセージの文言、コメントの有無
- フォーマット、テストの細部

## 採用解釈の開示
- 中規模以上 → 最終報告で「採用解釈 / 代替案 / 実施した検証」を開示する
- 単一ファイルの修正 → 不要（PR の説明で十分）
- 巻き戻る可能性のある暫定的な決定 → `{base}/decisions/` に暫定ステータスの決定として記録する（front-matter の status: provisional）

## 採用解釈が許容される範囲（autonomy_level に連動）


各 skill の `odd.yaml` で宣言された `autonomy_level` が、許容範囲を決定する:

| autonomy_level | 採用解釈の扱い |
|---|---|
| **L0**（情報表示）/ **L1**（軽量ユーティリティ）/ **L2**（中規模ワークフロー） | 採用解釈で進めてよい（最終報告で開示する） |
| **L3**（重量ワークフロー） | 進めてよいが、中規模以上では最終報告で「採用解釈 / 代替案 / 検証」の開示が必須 |
| **L4+**（自律 / 監督付き自動） | **事前確認が必須、採用解釈は不可** |
| **ODD なしの skill** | 暫定的に L0 として扱う（整理の際に正式な ODD を適用する） |

## 禁止事項
- 「おそらく」「たぶん」で不確実性を隠したまま断定すること（"Unverified:" プレフィックスは必須 — "Unverified:" または「未確認:」のいずれの表記も可）
- ゴール分岐を採用解釈のまま通過すること
- spec にない機能を追加すること
